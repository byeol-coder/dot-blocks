# DOT BLOCKS Blind-first QA

## 기능키 확정 동작 · 타이틀 · 점자 라인 — 검증 결과

- 낙하/퍼즐 두 모드의 키 분기 순서를 정적 분석해 `KeyFunction23`이 도달 가능함을 확인
  (앞선 분기에 catch-all 없음). 모드별 중복 매핑 없음
- `F2+F3`과 기존 패닝키가 **동일 함수**(`hardDrop()` / `placePuzzle()`)를 호출함을 코드로 확인
- 확정 동작 후 점자 라인이 `L #4 #19 (다음 I)` → `I #4 #15 (다음 S)`로 갱신되어
  블록이 실제로 고정되고 다음 블록이 올라오는 것을 확인
- h1 접근성 이름이 "DOT BLOCKS" 한 번만 낭독됨 (데스크톱·모바일 동일)
- 점자 비트 레이아웃을 기존 상수 6개와 대조 검증 후 블록 글자 7종 산출
- 닷패드 프레임 600 hex / 60×40 유지, 페이지 에러 없음

### 실제 닷패드에서 확인이 필요한 항목

1. **F2+F3 동시 입력이 실기 펌웨어에서 안정적으로 인식되는지** — 특히 빠른 연타 시
   F2 또는 F3 단독 입력으로 오인되어 의도치 않은 이동/회전이 일어나지 않는지
2. 20칸 점자 라인에 토큰 4개가 손끝 한 번에 스캔되는 분량인지
   (부담되면 다음 블록을 빼고 `F2+F4`에만 남기는 안으로 되돌릴 수 있음)
3. 수표 뒤 숫자와 블록 글자가 인접했을 때 혼동 여부 — `j`(2·4·5점)와 숫자 `0`은 같은 점형
4. 확정 키가 두 개(F2+F3, 패닝)인 것이 혼란스럽지 않은지

## 닷패드 숙련자 대응 — 검증 결과

- **점자 라인 실시간 갱신 확인** (진단 API `getAccessibilityState().brailleLine` 디코딩)
  - 낙하: `#4 #19` → 우로 이동 시 `#5 #19` `#6 #19` `#7 #18` `#8 #18`, 소프트드롭 후 `#8 #12`
  - 퍼즐: `#1 #1 o` → 커서 이동 시 `#1 #2 o` `#1 #3 o` `#1 #4 o` (o=놓을 수 있음, x=겹침)
  - 20셀(40 hex) 유지
- **점자 숫자 0 표준 대조**: 1~9는 기존에도 표준과 일치, 0만 `1·3·5·6점`으로 오류 → `2·4·5점`으로 교정
- **음성 길이 실측**: 간단 22자 / 다음·보관 19자 / 상세 135자 (기존 단일 안내 약 110자)
- 전체 키 스윕(←→↑↓ C S D V Q P Space) 후에도 `getDotpadFrame()` 600 hex, 60×40 유지, 페이지 에러 0건

### 실제 닷패드에서 확인 필요

1. 점자 라인의 `#열 #착지칸수`를 손가락으로 읽으며 동시에 촉각 보드를 탐색하는 것이 실제로 편한지
   (두 손 사용 가정 — 한 손은 점자 라인, 한 손은 핀 면)
2. 퍼즐 모드 `o`/`x` 표시가 촉각으로 즉시 구분되는지
3. 간단 상태(22자)만으로 충분한지, 아니면 착지 행 번호도 필요한지
4. `F2+F4`(다음·보관) 동시 입력이 기기 펌웨어에서 안정적으로 인식되는지

## 순수 배경 · 문구 축약 — 검증 결과

- 배경 5종 모두 WebP 변환 후 적용, 실패한 리소스 요청 없음 (파일 크기 29~78KB)
- 배경별 명도/분산을 5×6 격자로 측정해 UI 배치 결정:
  - 인트로 가로: 좌측 열 명도 18~96(저분산) → 문구 좌측 유지
  - 인트로 세로: **상단 행 23~31(저분산)** → 문구 상단 정렬로 변경
  - 설정·결과: 우측 열 9~26 → 서랍 위치와 부합
- 실제 렌더링에서 배경 적용 확인: 모바일 인트로 `intro-bg-mobile.webp` + `align-items:flex-start`, 제목 y123~206(빈 영역), 모바일 플레이 `play-bg-mobile.webp`
- 문구 영역 배경 명도 측정으로 가독성 확인 (플레이 p95=84, 설정 p95=211 → 흰 텍스트 충분히 판독 가능)
- 블록 색상은 테트리스 표준 배색과 겹치지 않는 기존 독자 팔레트를 그대로 유지 (변경 없음)
- CSS 중괄호 균형, 인라인 JavaScript `node --check` 통과, 데스크톱·모바일 페이지 에러 없음

### 실제 확인이 필요한 항목

1. 새 배경 위에서 캔버스 보드 테두리가 충분히 분리되어 보이는지 (특히 모바일 중간 밝은 띠)
2. 축약된 인트로 문구가 처음 접하는 사용자에게 충분한 안내인지 — 상세 안내는 "게임 방법 듣기"로 이동됨

## 레트로 칩튠 배경음악 — 검증 결과

- 편곡 검산: 8마디 × 16스텝 = 128스텝으로 정확히 떨어짐 (마디별 합계 전부 16 확인)
- 모의 AudioContext에서 128스텝 전체를 순회해 멜로디 온셋 37개가 모두 예상 스텝에 안착함을 확인
- 실제 Chromium에서 스케줄된 주파수 검증:
  - 1마디 `659(E5) 494(B4) 523(C5) 587(D5) 523(C5) 494(B4)`
  - 2마디 `440(A4) 440(A4) 523(C5) 659(E5) 587(D5) 523(C5)` → 코로베이니키 원곡 선율과 일치
  - 베이스 `165(E3) / 247(B3)` 루트–5도 교대 정상
- 설정 UI: 셀렉터 렌더링, 선택 시 엔진 즉시 반영, `localStorage` 저장, 새로고침 후 값 유지 확인
- 스타일 전환 시 `step`을 0으로 초기화해 루프가 깨끗하게 재시작됨
- HTML ID 104개 중복 없음, 인라인 JavaScript·`audio-engine.js` `node --check` 통과, 페이지 에러 없음

### 실제 사용자 테스트가 필요한 항목

1. 레트로 음악이 방향 효과음(스테레오 팬)과 위험 경고음을 가리지 않는지 — **시각장애인 사용자에게는 오디오가 주 정보 채널이므로 최우선 확인 항목**
2. 음성 안내 중 자동 감쇠(18%)가 칩튠에서도 충분한지 (기존 앰비언트 대비 배음이 많아 체감이 다를 수 있음)
3. 레벨 상승·위험 구간에서 템포가 빨라질 때 집중에 방해가 되지 않는지
4. 이어폰/스피커 각각에서 베이스(E3 165Hz)가 과하지 않은지
5. 장시간 플레이 시 128스텝(8마디) 루프의 반복 피로도

## 아케이드 게임감 강화 — 검증 결과

- 신규 함수 `showFx`/`bumpBoard`/`popStat` 및 호출부 이름 충돌 없음을 정적 분석으로 확인 (스코프별 카운트 일치)
- `lockDrop`(Drop)과 `placePuzzle`(Puzzle) 모두에서 기존 점수 계산식·오디오 타이밍·TTS 안내 문구는 변경 없이, 연출 트리거만 추가
- 헤드리스 Chromium에서 `#fxPop`/`#canvasWrap`/`#scoreValue`에 신규 클래스를 직접 토글해 애니메이션이 콘솔 에러 없이 렌더링되는 것을 확인
- `prefers-reduced-motion` 전역 리셋 규칙이 신규 애니메이션도 모두 포괄 (`fx-pop`만 모션 없이 즉시 표시되도록 별도 예외 처리)
- CSS 중괄호 균형, 인라인 JavaScript `node --check` 통과

## UI/UX 세련화 패스 — 작업 보고 (UI 작업 표준 원칙 기준)

- **재사용한 기존 토큰**: `--accent`, `--accent2`, `--ok`, `--danger`, `--muted` 그대로 유지
- **신규 공통 토큰**: `--cta-1`/`--cta-2`/`--cta-glow`(3곳에서 드리프트되던 CTA 그라데이션 통일), `--panel-deep`/`--panel-deep-2`/`--line-blue`/`--line-blue-soft`(반복되던 패널·보더 블루 통일), `--ease`/`--ease-out`(트랜지션 타이밍)
- **아이콘**: 유니코드 글리프(Ⅱ, ★) 2건을 발견해 기존 인라인 SVG 아이콘 시스템과 통일된 스타일로 교체 (Tabler 스타일 stroke 2px 유지, 신규 임의 SVG 없음)
- **중복 제거**: 동일 의도의 CTA 그라데이션 3벌(인트로 시작 버튼/플레이 헤더 로고/오버레이 확인 버튼)을 토큰 1벌로 통합
- **접근성 검증 결과**:
  - 색상 대비: 화이트 텍스트 on CTA 그라데이션 시작색 2.91:1 → `#0a86dd` 조정 후 3.84:1 (WCAG AA 큰글자 기준 3:1 충족)
  - 터치 타깃: `.btn`(39→44px), 홈/메뉴 버튼(40→44px), 드로어 닫기(40→44px), 플레이 컨트롤바 버튼(40→44px) 모두 44px 기준 충족. `max-height:720px and min-width:641px` 압축 쿼리(34px)는 터치가 아닌 데스크톱/노트북 좁은-세로 창 전용으로 판단해 기존 압축 규칙 유지
  - `prefers-reduced-motion`: 신규 트랜지션/애니메이션 전체를 포괄하도록 리셋 규칙 확장, 코드 검증 통과
  - 키보드 포커스: 기존 `body.kbd` 포커스 링 규칙 변경 없음
- **모션**: 신규 진입 애니메이션(인트로/플레이/드로어/오버레이)은 전부 `[hidden]` 속성 기반이라 JS 변경 없이 CSS만으로 구현 — 게임 로직 손상 위험 없음
- **코드 검증**: CSS 중괄호 균형(301/301), 인라인 JavaScript·`audio-engine.js`·`tts.js` `node --check` 전부 통과

## 실제 DotPad에서 반드시 확인할 항목

이 실행 환경에는 DotPad BLE 하드웨어가 없으므로 아래 항목은 실제 사용자 테스트가 필요합니다.

1. `cw`와 `ccw` 중 실제 세로 거치 방향과 일치하는 기본값
2. 고정 블록/현재 블록/예상 착지 세 질감의 구별 가능성
3. 4×3핀 셀에서 현재 블록 테두리가 손끝에 충분히 명확한지
4. 표면 스캔이 10개 열 높이를 빠르게 이해하는 데 도움이 되는지
5. 상단 위험 경고점이 게임 블록으로 오인되지 않는지
6. F1+F2, F3+F4, RPF4 동시/보조 키 코드가 기기 펌웨어별로 일치하는지
7. BLE 갱신 중 빠른 좌우 이동에서 프레임 누락이 없는지
8. 음성 안내가 재생되는 동안 음악 감쇠가 충분한지
9. 이어폰 사용 시 좌우 방향 효과음이 명확한지
10. 실제 시각장애인 사용자 3명 이상이 화면 없이 10분 이상 플레이 가능한지

## 권장 사용자 테스트 과업

### 낙하 모드

- I 블록을 왼쪽 끝과 오른쪽 끝까지 이동
- 블록을 2회 회전하고 예상 착지 위치 확인
- 블록 보관 후 다른 블록과 교체
- 표면 스캔으로 가장 높은 열 찾기
- 한 줄 완성 후 줄 삭제 피드백 설명
- 위험 경고 후 높이를 낮추기

### 블록 퍼즐

- 3개 블록을 차례로 선택
- 겹치는 자리의 X 질감 찾기
- 가로줄과 세로줄 각각 1회 삭제
- 상세 상태 읽기로 가장 많이 찬 행 찾기

## 합격 기준 제안

- 조작 성공률 90% 이상
- 현재 블록/고정 블록/착지 표시 구분 정확도 85% 이상
- 도움 없이 첫 줄 삭제까지 8분 이내
- 상태 읽기 요청 후 현재 열 범위 응답 정확도 90% 이상
- 게임 종료 이유를 모든 참가자가 설명 가능
